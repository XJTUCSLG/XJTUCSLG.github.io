如果项目目录里已经出现“最终版”“最终版二”和“这次真的最终版”，你需要的不是更好的文件名，而是一套记录变化的方法。Git 解决的核心问题，是把项目中值得保留的状态串成历史：现在改了什么，为什么改，什么时候开始出问题，哪些内容可以一起交给别人。学这个方向，不是先背几十条命令，而是先判断改动处在什么位置，再选择合适的操作。

## 知识地图：从文件到历史

先认清工作区、暂存区和提交。工作区是正在编辑的文件；暂存区是你为下一次提交挑选的内容；提交记录被选中内容形成的项目快照，并带有作者、时间和说明。一次提交不必包含当前所有改动。把几个无关问题混在一起，以后阅读、评审和撤销都会更困难。

Git 可以在本地工作，GitHub 是托管仓库和组织协作的平台，二者不能画等号。提交发生在本地，推送把提交同步到远程；没有推送的提交依然存在，但同学无法从远程看到。反过来，工作区里尚未提交的文件也不会因为一次推送就自动上传。

分支可以理解为指向某个提交的可移动名字。它让不同任务分别推进，再通过合并等方式把历史接起来。分支不是完整复制一份项目的压缩包，也不意味着不同人的修改永远不会冲突。冲突需要理解双方意图后处理，不能只看哪一边更新就一律保留。

撤销也有边界。丢弃工作区改动、调整暂存内容、撤销已经形成的提交，影响的对象并不一样。普通 diff 通常展示未暂存的改动，已暂存的内容需要另外检查；恢复文件也未必总是“回到上一条提交”，要看所选来源和文件当前状态。先辨认状态，再谈后悔药，能避免把想保留的内容一起丢掉。

## 推荐路线：读懂一条提交，再做自己的记录

从[《用 Git 管住代码：提交、回退与协作》](/blog/git-github-workflow/)开始。虽然文件名同时提到 GitHub，正文的主线是本地记录与日常同步。读完后，试着向同学解释“提交和推送有什么区别”“为什么先看差异再提交”。先抓住这两个问题，不必立刻掌握改写历史。

然后在一个不含重要资料和密钥的练习目录里做小改动。可以给简单程序补一句输出，再单独修正文档中的说明。每次修改前确认仓库和分支，修改后检查状态与差异，只选与这次目标相关的内容提交。提交信息写清变化的目的，别只写“更新”。完成后回看历史，确认两件事确实分成了两条能独立理解的记录。

接下来练习查证，而不是只练习保存。找出某次提交改了哪些文件，比较提交前后的内容，区分尚未暂存、已暂存和已经提交的变化。检查忽略规则是否覆盖生成物和本地敏感文件。忽略规则通常不会自动停止跟踪已经入库的文件，也不会把历史里的秘密抹掉；检查当前文件和历史是不同的责任。

再给练习增加一个任务分支。在分支上完成一项小修改，观察分支名字与提交之间的关系，然后比较它与原来的主线。先尝试没有冲突的情况，弄清改动如何进入主线，再在可丢弃的练习仓库里理解冲突。目标是能解释双方分别改了什么，以及合并后的结果为何合理，而不是消掉报错文字就算结束。

有了本地模型，再读[《第一个开源 PR：从 issue 到 merged》](/blog/first-open-source-pr/)。这时先关注任务分支、差异检查、推送目标和提交范围，把 Git 放进协作流程中。PR 的沟通、评审和平台检查留给[《GitHub 与协作导读》](/guides/github-and-collaboration/)展开。阅读时可以画出本地仓库、自己的远程仓库和上游仓库，标注提交在哪里生成、推送到哪里，比只抄命令更容易看出方向是否正确。

## 遇到后悔药需求，先问三个问题

第一，内容是否已经被记录？Git 不能保证找回未跟踪文件、未保存的编辑或从未提交就丢弃的修改。第二，要撤销的是哪一部分？先看差异，必要时另留副本，不要为了“清理状态”直接丢弃内容。第三，历史是否已经共享？用新提交表达撤销，通常更便于大家理解，但仍需验证结果；多人共享或正在评审的分支若要改写历史，应先沟通并遵守仓库规范。带保护条件的强制推送也不保证无风险。

想把配置作为后续练习，可以读[《把配置放进 Git：dotfiles 的第一版》](/blog/dotfiles-in-git/)中的分类与独立仓库思路。文中迁移命令仍需校核，操作前备份并核对路径，不要把家目录整体纳入版本控制。密钥不应提交；若令牌已经入库，先吊销或更换，删除当前文件并不等于消除泄露。

## 完成标准与下一步

起步阶段可以用这些成果验收：

- 能解释工作区、暂存区、提交、本地仓库和远程仓库的区别。
- 能按一个明确目的选择提交内容，且历史里没有顺手带入的无关文件。
- 能查看某次变化，说明它解决什么问题，而不是只知道提交编号。
- 能确认当前分支与推送目标，知道别人能否看到自己的提交。
- 面对撤销需求，能先说明改动是否提交、是否共享，再决定下一步。

如果连练习程序都无法启动，回到[《环境与命令行导读》](/guides/environment-and-command-line/)补齐环境验证；如果本地记录已经清楚，就转向[《GitHub 与协作导读》](/guides/github-and-collaboration/)，练习让别人读懂并评审你的改动。本站计划中的《rebase、cherry-pick 与各种后悔药》和《团队里什么时候该开分支》仍是待写专题，不应当作已有教程。先把小而清楚的提交做稳，比提前收集复杂命令更值得。
