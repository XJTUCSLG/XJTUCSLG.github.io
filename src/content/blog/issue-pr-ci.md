上篇说到 GitHub 是放在网上的仓库。这篇解决下一个问题：写代码从一个人变成一群人，靠脑子记就不够了。谁在做什么？做到哪了？他改的代码能不能合进来？这三件事，就是 issue、PR、CI 各自要解决的。

## 为什么需要：一个人和一群人的区别

一个人写代码，"要做什么"记在脑子里就行。功能做完了，自己看一眼，合了。

一群人就不行了。先是分工乱：五个人同时写，群里吼一句"你登录那块写完了吗"，消息一刷就没了，没人知道各自做到哪一步。

然后是合并险：他说"我改好了"，代码直接合进主分支，结果把别人的改动覆盖了，或者带进去一个 bug，所有人都得停下来修。

最后是检查累：每次合并前找个人把代码从头看到尾，又累又会漏，漏一次就线上见。

所以需要三个东西：一个记事的地方，一个"合进来之前先看看"的流程，一个自动跑检查的机器。对应过来就是 issue、PR、CI。

## 它们在流程里的位置

```mermaid
flowchart LR
  A["issue<br/>要做什么"] --> B["开分支写代码"]
  B --> C["开 PR<br/>请求合并"]
  C --> D["CI 自动检查"]
  D --> E["有人看代码<br/>没问题就合"]
  E --> F["issue 关闭"]
```

比如这样走一遍。有人在 issue 里记了一条"登录页验证码不显示"，你领了，开个分支修好，push 上去，开个 PR 说"我改完了，合进来吧"。CI 自动跑测试，通过了。维护者看了一遍代码，没问题，点合并，issue 自动关闭。

先有 issue 记录要做什么，才有 PR 请求合并；PR 开了，CI 才有东西可查。三件套得串起来看。

## 具体用法和时机

### issue：把"要做什么"记下来

什么时候开？发现 bug、有新需求，或者拿不准要不要做，先开个 issue 把事说明白。

怎么写？标题一句话讲清是什么事，正文给背景或复现步骤，报错截图和日志贴上。对比一下：

- "出 bug 了"——没人知道回你什么。
- "登录页验证码不显示（Chrome 124，控制台报错 xxx）"——接的人一看就知道从哪下手。

认领了就把 assignee 指给自己，别人看到这事有人在做了，就不会重复开。

### PR：合并之前先给人看

什么时候开？功能写完、想合进主分支的时候。PR 里写清楚三样：改了什么，为什么这么改，自己是怎么测的。标题写人话，"修复登录页验证码不显示"比"fix"强。

```bash
git switch -c fix/captcha       # 开个分支，在分支上改
# ... 改代码，commit ...
git push -u origin fix/captcha  # 推上去
# 然后去 GitHub 网页上点 "Compare & pull request"
```

一次 PR 只做一件事。攒个大 PR，别人看不动，CI 挂了也不知道是哪改坏的。

### CI：自动跑的检查

什么时候跑？每次 push 自动跑，不用你管。常见的就两类：跑测试，查代码格式。

挂了就点进日志，看哪一步红了，本地修好再 push，它会重新跑。CI 拦的是坏代码，挂了别慌，一个个修。

### 在 issue 和 PR 里学交流

issue 和 PR 都是跟人对话的地方。刚开始协作，最重要的不是"敢不敢问"，是"能不能把事说清楚、把话接住"。

- 提 issue 之前先自己排查一遍。报错贴全，复现步骤写清，期望是什么也写上。信息给够，别人才接得住。
- 开 PR 是请人看代码。描述里写改了什么、为什么这么改。别人提了意见，先回一句"收到"再改，别已读不回。
- 被指出问题，先看他说的对不对。对就改，改完回复"改好了"；有不同想法就讲理由，贴代码或截图说明。
- 小改动也要开 PR 吗？看仓库规矩。自己的小项目直接合没问题；别人的项目、人多的项目，走 PR 是基本礼仪。
