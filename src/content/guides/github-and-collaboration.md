代码推到网上，只说明别人有机会看到它，还不等于协作已经完成。一个同学要理解问题、复现现象、判断改动是否合适，维护者还要考虑项目约定和后续成本。GitHub 与协作这个方向，解决的就是这些人与人之间的交接：问题怎么说清，修改怎么送审，意见怎么回应，检查结果怎么解释。第一次参与可以很小，修正文档、补充复现信息或完善一个边界测试，都有实际价值。

## 知识地图：问题、提案、证据和决定

Issue 是讨论问题和需求的入口。一个有用的 issue 应说明预期行为、实际行为、环境以及复现步骤，而不只是“这里坏了”。需求类问题则需要解释使用场景和希望改善的结果。开 issue 不自动获得任务分配，也不代表维护者已经同意某种方案；改动较大时，先确认方向更省力。

PR 是请求把一个分支的改动合入目标分支的提案。它既包含代码差异，也承载目的、验证方式和讨论记录。推送成功不是合并成功，开 PR 也不是要求维护者立刻接受。Reviewer 关注的可能包括正确性、范围、可维护性和项目风格，意见需要逐项理解，不必把所有讨论都当成对个人的评价。

CI 是自动运行项目所配置检查的机制。它可能执行构建、测试或格式检查，具体做什么、何时触发，要看仓库工作流配置。绿色只能说明这些已执行检查通过，不能证明代码完全正确，也不能单独证明 PR 可以合并。红色也不一定全是你的代码导致的，环境和基础设施同样可能失败，需要阅读对应日志后再判断。

Fork 是平台上的仓库副本，clone 是把仓库取到本地，branch 是仓库中的任务分支。三者不是同一层东西。没有上游写权限时，常见做法是在自己的 fork 推送任务分支，再向上游提出 PR；有权限的团队也可能直接在同一仓库协作。先确认权限和贡献规范，不要把某一种流程当成所有项目的要求。

## 推荐路线：先读约定，再选择小问题

前置是能够检查差异、做清楚的提交，并分清本地与远程。如果还不熟悉这些概念，先读[《用 Git 管住代码：提交、回退与协作》](/blog/git-github-workflow/)，或回到[《Git 导读》](/guides/git/)。环境尚未跑通的同学，可以先按[《环境搭建：从一台新电脑到能写代码》](/blog/dev-environment-from-zero/)验证基础工具。

正式动手时，先看目标仓库的 README、贡献说明以及与任务有关的目录。了解如何安装、运行和验证，确认项目是否仍在接受贡献。查一下已有 issue 和 PR，避免重复解决同一个问题。若是范围较大的改动，用简短提案确认目标；若只是明确的文档修正，也要遵守项目对提交和 PR 的要求。

随后读[《第一个开源 PR：从 issue 到 merged》](/blog/first-open-source-pr/)，把它当作一次流程示范，而不是所有仓库都通用的脚本。选一个自己能解释的小问题，在独立任务分支里修改，确认推送目标属于自己有权限写入的仓库。不要把无关格式化、依赖升级和个人配置一起带上，让评审者能看出改动与问题之间的关系。

验证要以当前仓库要求为准。文档修改检查文字、路径、链接和展示；代码修改执行适用的测试与构建，并记录结果。本站 README 还记录了特定 Windows 环境下构建与检查的已知问题，遇到同类失败时应报告环境、命令和错误，不可写成“已通过”。自动检查则以实际工作流为准：查看触发条件、执行任务和日志，弄清本地验证与平台检查分别提供了什么证据。

## 把评审当成持续交接

PR 描述至少回答四个问题：改了什么，为什么要改，怎么验证，还有哪些限制。关联已有 issue 时核对编号，不要为了套模板随意写自动关闭关键词。涉及截图或日志，先移除令牌、邮箱和其他不必公开的信息。提交说明和 PR 描述都应准确，不能把没有执行的检查写成成功。

收到评审意见后，先区分事实问题、项目规范和方案取舍。需要修改就在同一任务分支继续提交，PR 通常会随推送更新；有不同意见则解释理由和代价。多人共享分支或正在评审的分支若要改写历史，先沟通并遵守仓库约定，不要把重新整理历史当作每次同步的必做步骤。带保护条件的强制推送也不保证毫无风险，协作时仍要确认其他人的工作与评审上下文不会被意外影响。

维护者没有立即回复时，可以在合理间隔后礼貌补充进展或询问，不必刷屏。合并由维护者按项目标准决定，可能还需要额外检查，也可能因范围或优先级暂不接受。把讨论结论留下来，比只追求页面出现“merged”更能帮助下一位参与者。

合并后也值得回看一次：问题是否真正解决，文档是否需要补充，任务分支是否可以按项目约定清理。若未合并，记录原因和已经得到的反馈，避免下次重复走弯路。一次贡献的结果不只有代码进入主线，也包括更清楚的问题描述和可供后来者使用的验证信息。

## 完成标准与下一步

一次起步练习完成后，你应能留下这些可检查的结果：

- 问题或任务描述清楚，别人知道如何复现或验收。
- 仓库、权限、任务分支和目标分支确认无误。
- 改动只服务当前目标，PR 描述与实际差异一致。
- 验证过程有记录，失败与未执行的检查没有被隐去。
- 能回应评审并说明剩余问题，不把合并结果完全当作个人能力评分。

完成练习不要求首次 PR 必须被合并，也不承诺等待多久。之后可以选一个稍复杂的问题，继续练习复现、测试和沟通；若差异或历史难以理解，就回到[《Git 导读》](/guides/git/)，若本地无法验证，就回到[《环境与命令行导读》](/guides/environment-and-command-line/)。本站的《issue、PR、CI 各自解决什么问题》和《给一个不认识的项目提 PR》仍是待写专题。眼下先交出一份别人能接着检查和讨论的小改动，就是可靠的协作起点。
