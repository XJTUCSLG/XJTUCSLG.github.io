想象这样一个场景：这学期有门课要交大作业，你写了个几百行的 Python 脚本。第一版能跑，你接着加功能。加到第三天，程序崩了。你想回到"昨天还能跑"的样子，却发现这三天里改了几十处，根本想不起来是哪一处改坏的，只能一行行翻，或者重写。

这篇读完，你会知道为什么写代码需要把每一次改动记下来，Git 在你每天的开发流程里站在哪个位置，以及什么时候提交、什么时候推送、搞砸了怎么退。

## 为什么要用 Git 记录

写代码这件事，最大的特点是不确定。你敲下这行代码的时候，不知道它会不会引入 bug；今天能跑的代码，明天加个功能可能就崩了，崩在哪还得现找。

因为不确定，所以每次改动都要留档。Git 的提交（commit）就是把"这一刻整个项目的状态"拍一张快照，附上一句话说明改了什么。

一次快照里记的东西很具体：改了哪些文件，每个文件增删了哪些行，谁在什么时候改的，以及为什么改（就是提交信息里那句话）。看一次真实的提交：

```bash
git show --stat  # 看最近一次提交里记了什么
# commit 3a2f1b9
# Author: 你  Date: 今天 14:32
#     登录页加上验证码
#
#  login.html | 12 ++++++++++++
#  style.css  |  3 +++
```

`+` 是新增的行，`-` 是删掉的行。Git 记到行的粒度，所以回滚能精确回到"改之前"的样子。压缩包只知道"有这么个版本"，Git 知道这个版本里每一行是加是减。

有了记录，回滚才有意义。改崩了，回到上一个能跑的快照就行。回滚能成立，全靠之前每一步都记下来了。

那为什么不用压缩包？把文件夹复制一份改名，粒度太粗了。你只知道"有这么个版本"，不知道这个版本到底改了什么、为什么改。五个压缩包之后，哪个是哪个全靠猜。Git 记的是每一次改动的内容和原因，`git log` 一翻，全在。

记录还有两个顺带的好处。想知道"我昨天到底改了什么"，翻记录，不用靠记忆。两个人改同一份代码，各自在自己的线上走，最后合起来，不会互相覆盖。分支就是干这个的，下一篇细讲。

## Git 在开发流程里的位置

你每天的流程其实就四步：

```mermaid
flowchart LR
  A["写代码"] --> B["add / commit<br/>本地存档"]
  B --> C["push<br/>同步到 GitHub"]
  C --> D["别人 pull<br/>拿下来接着干"]
```

九成时间你在最左边：写代码。写完一个小功能、能跑起来了，`commit` 在本地记一笔。临下班、换电脑，或者要给别人看，`push` 把本地的记录同步到 GitHub。别人 `pull` 下来，接着干。

GitHub 是什么？放在网上的仓库。你的 push 到了那里，别人的 pull 从那里拿。

仓库有了，协作才有地方发生。最常用的三件套：

| 工具 | 它解决什么问题 |
| --- | --- |
| issue | 把"要做什么"记下来：需求、bug 都可以是一条 issue，能指派给人、能讨论 |
| PR | "我改完了，合进来吧"：合并之前别人先看一遍代码，没问题再合进主分支 |
| CI | 每次 push 自动跑一遍检查：测试挂了就别合，把坏代码拦在外面 |

这三个下一篇细讲，这里先有个印象：它们都是建在仓库之上的。

> 记住这个顺序：先有本地的提交，才有推送。push 推送的是提交，本地没有提交，push 就没东西可推。

## 具体用法和时机

**什么时候 commit：一个小功能写完、能跑起来的时候。**别攒着，一天提交三五次很正常。提交信息写人话，说明这次改了什么，以后你自己翻记录全靠这句话。

```bash
git add .                       # 把改动放进暂存区：这次我要提交这些
git commit -m "登录页加上验证码"  # 记一笔：说明这次改了什么
```

**什么时候 push：收工前、换电脑前。**顺序别反：先 commit 再 push。

```bash
git push  # 把本地的提交同步到 GitHub
```

**什么时候看 log 和 diff：忘了自己改了什么的时候。**

```bash
git log --oneline  # 一行一条，看提交历史
git diff           # 看还没提交的改动有哪些
```

**搞砸了怎么退，看改动走到哪一步。**还没 commit，改动还在工作区，直接丢弃：

```bash
git restore <file>  # 丢弃这个文件的改动，回到上次提交的状态
```

已经 commit 了但想反悔，用 revert 生成一个"撤销"的新提交，记录还在，最安全：

```bash
git revert HEAD  # 生成一个新提交，把上一次提交的效果撤销掉
```

更复杂的后悔药，比如改写已经推上去的历史，放在 git 实践篇。
